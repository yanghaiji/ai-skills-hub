### 描述
**需求明确化技能**  
通过系统化澄清和 100 分评分系统，自动把模糊需求转化为可执行的 PRD。

### 指令
被调用时，检测模糊需求：

**模糊功能请求**
- 用户说：“加登录功能”“实现支付”“创建仪表盘”
- 缺失：怎么做、用什么技术、有什么约束？

**缺失技术背景**
- 没提技术栈
- 没识别集成点
- 没提性能 / 安全约束

**规格不完整**
- 没有验收标准
- 没有成功指标
- 没考虑边界情况
- 没提错误处理

**范围模糊**
- 边界不清楚，比如“用户管理”到底包括什么？
- 没有区分 MVP 和未来增强
- 没有说明“不包含什么”

**不要激活的情况：**
- 提到具体文件路径，例如 `auth.go:45`
- 包含代码片段
- 引用了已有函数 / 类
- Bug 修复且有明确复现步骤

---

## 核心原则

### 1. 系统化提问
- 问聚焦、具体的问题
- 每轮只问一个类别，2-3 个问题
- 基于之前的回答继续追问
- 避免让用户负担过重

### 2. 质量驱动迭代
- 持续评估清晰度分数，0-100
- 系统识别信息缺口
- 迭代到 ≥ 90 分
- 记录所有澄清轮次

### 3. 可执行输出
- 生成具体规格
- 包含可衡量的验收标准
- 提供可执行阶段
- 能直接进入实现

## 澄清流程

### 第 1 步：初始需求分析
输入：用户的需求描述

任务：
- 解析并理解核心需求
- 生成功能名，kebab-case 格式
- 确定文档版本，默认 1.0，除非用户指定
- 确保 `./docs/prds/` 存在，用于输出 PRD
- 进行初始清晰度评估，0-100

评分标准：

| 维度 | 分数 |
|---|---|
| 功能清晰度 | /30 |
| - 清晰输入 / 输出 | 10 |
| - 用户交互已定义 | 10 |
| - 成功标准已说明 | 10 |
| 技术具体性 | /25 |
| - 提到技术栈 | 8 |
| - 识别集成点 | 8 |
| - 明确约束 | 9 |
| 实现完整性 | /25 |
| - 考虑边界情况 | 8 |
| - 提到错误处理 | 9 |
| - 明确数据验证 | 8 |
| 业务背景 | /20 |
| - 问题陈述清晰 | 7 |
| - 目标用户明确 | 7 |
| - 成功指标明确 | 6 |

初始回复格式：

> 我理解你的需求。让我帮你细化这个规格。  
> **当前清晰度分数**：X/100  
> **清楚的部分**：...  
> **需要澄清的部分**：...  
> 让我系统化地澄清这些点……

---

### 第 2 步：差距分析
从四个维度识别缺失信息：

1. **功能范围**
    - 核心功能是什么？
    - 边界是什么？
    - 什么不在范围内？
    - 有哪些边界情况？

2. **用户交互**
    - 用户如何交互？
    - 输入是什么？
    - 输出是什么？
    - 成功 / 失败场景是什么？

3. **技术约束**
    - 性能要求？
    - 兼容性要求？
    - 安全考虑？
    - 可扩展性需求？

4. **业务价值**
    - 解决什么问题？
    - 目标用户是谁？
    - 成功指标是什么？
    - 优先级是什么？

---

### 第 3 步：交互式澄清
提问策略：
- 从影响最大的缺口开始
- 每轮问 2-3 个问题
- 逐步建立上下文
- 使用用户的语言
- 有帮助时提供例子

问题格式：

> 我需要澄清以下几点，才能完成需求文档：
>
> 1. **[类别]**：[具体问题]？
     >    - 例如：[有帮助的示例]
>
> 2. **[类别]**：[具体问题]？
>
> 3. **[类别]**：[具体问题]？
>
> 请提供你的回答，我会继续完善 PRD。

每次用户回复后：
- 更新清晰度分数
- 把新信息记录到 PRD 草稿中
- 识别剩余缺口
- 如果分数 < 90：继续下一轮提问
- 如果分数 ≥ 90：进入 PRD 生成

分数更新格式：

> 感谢补充信息！  
> **清晰度分数更新**：X/100 → Y/100  
> **新澄清内容**：...  
> **剩余待澄清点**：...  
> 如果 < 90：继续下一轮问题。  
> 如果 ≥ 90：完美！我现在生成完整 PRD 文档……

---

### 第 4 步：生成 PRD
一旦清晰度 ≥ 90，生成完整 PRD。

输出文件：

`./docs/prds/{feature_name}-v{version}-prd.md`

使用 Write 工具创建或更新这个文件。版本来自 PRD 中记录的文档版本，默认 1.0。

PRD 文档结构包括：

- **需求描述**
    - 背景：业务问题、目标用户、价值主张
    - 功能概览：核心功能、功能边界、用户场景
    - 详细需求：输入 / 输出、用户交互、数据需求、边界情况

- **设计决策**
    - 技术方案：架构选择、关键组件、数据存储、接口设计
    - 约束：性能、兼容性、安全、可扩展性
    - 风险评估：技术风险、依赖风险、进度风险

- **验收标准**
    - 功能验收
    - 质量标准
    - 用户验收

- **执行阶段**
    - 阶段 1：准备
    - 阶段 2：核心开发
    - 阶段 3：集成与测试
    - 阶段 4：部署

文末包含：

- 文档版本：1.0
- 创建时间：{timestamp}
- 澄清轮次：{clarification_rounds}
- 质量分数：{quality_score}/100

## 行为准则

**应该做：**
- 问具体、有针对性的问题
- 基于之前的回答继续推进
- 提供例子引导用户
- 保持对话式语气
- 在 PRD 中总结澄清轮次
- 使用清晰、专业的英文
- 生成具体规格
- 在分数 ≥ 90 前保持澄清模式

**不应该做：**
- 一次问完所有问题
- 未经确认就做假设
- 在 90 分前生成 PRD
- 跳过任何必需章节
- 使用模糊、抽象语言
- 没有用户回复就继续推进
- 过早退出技能模式

---

## 成功标准
- 清晰度分数 ≥ 90/100
- 所有 PRD 章节完整且有实质内容
- 验收标准可勾选，使用 `- [ ]` 格式
- 执行阶段可操作，有具体任务
- 用户批准最终 PRD
- 准备好交接给开发
