# 审查报告输出格式模板

Agent 输出审查报告时，必须严格按照本模板的结构组织内容。

---

## 完整报告模板

```markdown
## 📋 Code Review 报告

- **审查范围**：[N] 个文件，[N] 行新增，[N] 行删除
- **变更类型**：[新功能 / Bug修复 / 重构 / 配置变更]
- **涉及技术栈**：[Java / TypeScript / Python / SQL / ...]
- **审查时间**：[YYYY-MM-DD]
- **总体评价**：[✅ 通过 / ⚠️ 需修改后通过 / ❌ 需重大修改]

---

### 📊 问题统计

| 等级 | 数量 | 说明 |
|------|------|------|
| 🔴 Blocker | N | 必须修复：Bug、安全漏洞、数据风险 |
| 🟠 Major | N | 强烈建议修复：性能、并发、错误处理 |
| 🟡 Minor | N | 建议修复：命名、注释、代码风格 |
| 💡 Suggestion | N | 优化建议：更好的实现方式 |

---

### 🔴 Blocker 问题

#### [B1] 问题标题

- **文件**：`path/to/file.java` L42-L48
- **维度**：[正确性/安全性/性能/可维护性/规范性]
- **依据**：[引用规范条目，如"java-coding-standards 九、异常处理"]

**问题描述**：
简要说明问题是什么、为什么是问题。

**建议修改**：
```java
// 修改后的代码示例
```

**影响说明**：
解释可能造成的具体影响（数据丢失、安全漏洞等）。

---

### 🟠 Major 问题

#### [M1] 问题标题

- **文件**：`path/to/file.java` L15-L20
- **维度**：[维度]
- **依据**：[规范条目]

**问题描述**：
简要说明。

**建议修改**：
```java
// 修改后的代码示例
```

---

### 🟡 Minor 问题

#### [m1] 问题标题

- **文件**：`path/to/file.java` L33
- **维度**：[维度]

**问题描述**：
简要说明。

**建议修改**：
简要说明修改方式。

---

### 💡 Suggestion

#### [S1] 建议标题

- **文件**：`path/to/file.java` L50-L60
- **维度**：[维度]

**建议说明**：
说明为什么这样做更好，给出示例。

---

### ✅ 亮点

- [值得肯定的设计或实现，如"使用了策略模式消除了 if-else 分支，扩展性好"]
- [如"测试覆盖充分，包含边界场景"]

---

### 📝 总结

[1-3 句话概括审查结论，列出最关键的改进方向]

**建议**：[通过 / 修改后通过 / 重大修改后重新审查]
```

---

## 总体评价判断标准

| 评价 | 条件 |
|------|------|
| ✅ 通过 | 无 Blocker，Major ≤ 2 |
| ⚠️ 需修改后通过 | 有 Blocker ≤ 1，或 Major ≤ 5 |
| ❌ 需重大修改 | 有 Blocker ≥ 2，或 Major > 5，或存在严重安全漏洞 |

---

## 输出注意事项

1. **问题编号连续**：Blocker 用 B1/B2...，Major 用 M1/M2...，Minor 用 m1/m2...，Suggestion 用 S1/S2...
2. **必须引用规范**：每个问题尽量引用具体规范条目（来自联动的 Skill）
3. **必须给出修改建议**：不只指出问题，要给出可执行的修改方案
4. **文件定位精确**：标注文件名和行号范围，方便开发者定位
5. **亮点不可省略**：即使问题很多，也要找出至少一个亮点（鼓励良好实践）
6. **总结必须精炼**：不超过 3 句话，聚焦最关键的改进方向
